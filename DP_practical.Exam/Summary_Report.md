# Summary Report — Customer Purchase Propensity Pipeline

## What was done
Data was loaded from four sources — `customers.csv`, `transactions.json`, `products.sql` (via `sqlite3`), and the `dummyjson.com/users` API — and merged on `customer_id` / `product_id` into a single 8-row, 25-column dataset. From there the full preprocessing pipeline was applied: EDA (univariate histograms + skew check, bivariate correlation/boxplots of income & purchases against the target, multivariate heatmap + pairplot), 6 missing-data techniques (Simple/mode/indicator+random-sample/KNN/MICE/complete-case), 3 outlier-detection methods (Z-score, IQR, percentile) plus Winsorizing, mixed-ID and datetime handling, 3 encoding schemes (label, one-hot, ordinal) plus income binning, 5 scalers (Standard/MinMax/MaxAbs/Robust/Normalizer) plus a `ColumnTransformer`, and feature construction (interaction feature, log/sqrt/reciprocal via `FunctionTransformer`, Box-Cox/Yeo-Johnson via `PowerTransformer`, quantile binning, binarization). The final engineered dataset (63 columns) was exported to `processed_customer_data.csv`.

## Biggest issues with the raw data
1. **Scale mismatch**: `customers.csv` only has 8 rows, while the brief assumes columns the raw files simply don't contain (`signup_date`, `education`, `satisfaction_level`, a `purchased` target). These were synthesized with a fixed seed (`np.random.default_rng(42)`) so the required missing-value/outlier/mixed-format demonstrations would have real material to work on — this is a data-availability gap, not something hidden from raw values.
2. **Mixed-format IDs**: some `customer_id` values were embedded in strings like `"CUST101"` rather than plain integers, requiring regex extraction before they could be used as a numeric key.
3. **Bad/extreme values**: one negative income (`-500`) and one implausible age (`121`) were present — classic data-entry errors that Z-score/IQR/percentile checks caught differently (IQR and percentile flagged more of them than Z-score on this small sample).
4. **Missingness spread unevenly** across `income` (20%), `education` (15%), `age`/`satisfaction_level` (~12%), and `last_purchase_date` (10%) — high enough that Complete Case Analysis alone would have discarded 3 of 8 rows (37.5%), too costly on such a small dataset.
5. **API mismatch**: the public API returns arbitrary users unrelated to the local customer IDs, so a synthetic `customer_id = api_user_id + 100` mapping was used purely to demonstrate a 4th data source join (documented, not treated as a real key).

## Which imputation and scaling worked best
- **Imputation**: KNN Imputer was used for `income`/`age`/`total_purchases` because it borrows information from correlated numeric neighbors rather than collapsing everyone to one mean/mode — meaningfully better than Simple Imputer on a dataset this small and correlated. SimpleImputer (most-frequent) was kept for the two categorical columns since there's no clear multivariate categorical relationship to exploit. Complete Case Analysis and plain mode-imputation were rejected — the former loses too much data, the latter ignores relationships between features.
- **Scaling**: `RobustScaler` is the most defensible default for `income` given the injected outliers (it uses median/IQR, so it isn't dragged around by the ₹9.5L and −₹500 entries); `StandardScaler` is fine for `age`, which is closer to normal after Winsorizing. All five scalers were computed for comparison in the notebook, but Robust + Standard (via the `ColumnTransformer`) is the recommended combination going into modeling.
